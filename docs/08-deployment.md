# Развёртывание: запуск сервера, opencode, туннель, настройка навыка

Документ пошагово описывает, как поднять R2D2 с нуля: от зависимостей до
работающего навыка на Станции.

Порядок важен: сначала поднимается **opencode-сервер** (это теперь мозг), потом
сам R2D2, потом туннель, потом регистрация навыка.

## 0. Предварительные требования

- Linux-ноутбук с Python 3.11+ и доступом в интернет.
- **Установленный opencode CLI** — см. шаг 0.1, без него шаг 2 не запускается.
- Рабочий каталог для сессий, отдельный от домашней папки: `$HOME/r2d2-workspace`
  (в примерах ниже — `/home/<user>/r2d2-workspace`). Его нужно создать заранее:
  сервер использует свой cwd как каталог сессий по умолчанию.
- Яндекс-аккаунт (тот же, что на Станции).
- Для Telegram — аккаунт и бот (см. шаг 6). **И** обязательная привязка
  `R2D2_TG_APPLICATION_ID` (см. шаг 6.1): без неё брокер разрешений и доставка
  длинных результатов не работают вообще.
- Ключи цепочки фолбэков (см. шаг 5). **Без них система работает** — но только
  если работает opencode-маршрут: без opencode И без ключей цепочки отвечать
  нечем (см. шаг 2.5).

## 0.1. Установка opencode

R2D2 не ставит opencode и не управляет им: нужен CLI, который умеет `opencode
serve`. Ниже — канал, установленный **на машине, где этот проект собран**: он
проверен по трём независимым следам и воспроизводим любой читатель.

**Вариант А — официальный установочный скрипт (рекомендуется).**

```bash
curl -fsSL https://opencode.ai/install | bash
~/.opencode/bin/opencode --version
```

Откуда известно, что это тот самый канал, а не догадка. Бинарь opencode сам
содержит установщик: он запрашивает `https://opencode.ai/install`, читает ответ как
текст и подаёт его на stdin в `bash` (в `sh`, если `bash` не найден), с
переменной окружения `VERSION=<версия>`. Тот же бинарь умеет называть способ своей
установки и для бинаря, лежащего в `~/.opencode/bin`, отвечает `curl` — то есть
именно этот канал и кладёт бинарь в `~/.opencode/bin`. Обновление и удаление —
той же кодовой базой: `opencode upgrade [версия]`, `opencode uninstall`.

**Вариант Б — npm.** На этой машине пакет `opencode-ai` установлен дважды:
1.18.5 системно и 1.18.21 в пользовательский префикс.

```bash
npm install -g opencode-ai
command -v opencode && opencode --version
```

Проверяемо по содержимому самого пакета: `opencode-ai` объявляет
`bin.opencode = ./bin/opencode.exe`, а его `postinstall`
(`node ./postinstall.mjs`) копирует нативный бинарь из optional-зависимости
`opencode-<os>-<arch>` (для этой машины — `opencode-linux-x64`) в `bin/`.
Расширение `.exe` здесь обманчиво: файл — обычный ELF для Linux.

> **Вариант В (Homebrew, формула `anomalyco/tap/opencode`) здесь НЕ проверен.**
> Это имя формулы знает сам бинарь opencode (он вызывает
> `brew list --formula anomalyco/tap/opencode`), но Homebrew на машине проекта не
> установлен. Упоминается, чтобы не выглядеть полнотой, которой здесь нет.

**Чего установить нельзя.** `opencode` из `PATH` на этой машине — версии 1.18.5,
1.18.21 и 1.18.33 одновременно в трёх разных местах, и `opencode` без полного
пути разрешается в ту копию, которая первой в `PATH`. Поэтому бинарь в
развёртывании закрепляется явно: `R2D2_OC_BIN` называет нужную сборку (шаг 2.3),
а когда он не задан — берётся `~/.opencode/bin/opencode`, и лаунчер отказывается,
если в `PATH` кандидатов больше одного, перечисляя их, вместо того чтобы выбрать
первый.

**Честный пробел.** То, какая из двух команд выше положила сюда
`~/.opencode/bin/opencode` версии **1.18.33**, на машине **не зафиксировано**:
npm-каналы дают 1.18.21 и 1.18.5, а установочного скрипта, журнала установки или
lock-записи, которые это объясняли бы, на диске нет. Единственное, что можно
сказать, — то, что говорит сам бинарь о себе: экземпляр в `.opencode/bin` он
считает установленным через `curl`-канал. Поэтому ниже «1.18.32» из старой
замерной записи и «1.18.33» на диске — это версии, на которых проект работал, а
не требование: **R2D2 проверяет не версию, а каталог моделей** (шаг 2.5).

## 2. Установка opencode-сервера (мозг)

### 2.0. Одна команда

```bash
bash scripts/install.sh
```

Она идемпотентна: повторный запуск ничего не ломает и ничего не переписывает по
своему усмотрению, поэтому ею же чинят машину, у которой разъехались пути.
Что она делает:

| что | куда | чем |
|---|---|---|
| матрица разрешений | `~/.r2d2/opencode/opencode.json` | `install_r2d2_opencode_config.sh` |
| шим `r2d2_do` | `~/.r2d2/r2d2_do.py` (0755) | там же |
| systemd-юнит | `${XDG_CONFIG_HOME:-$HOME/.config}/systemd/user/r2d2-opencode.service` | там же (`--unit`) |
| каталог сессий | `$HOME/r2d2-workspace` (0700) | сам скрипт |
| `.env.oc` | корень checkout, из `.env.oc.example` (0600) | сам скрипт |

Чего она **не** делает и почему: не пишет пароль (его выдумывает оператор, и
пустой пароль — это не пароль, см. 2.3), ничего не запускает и не останавливает
(процесс opencode принадлежит юниту, а не R2D2), и не включает юнит
(включение — отдельное решение). В конце она печатает оставшиеся шаги.

Нужен нестандартный каталог сессий или другой префикс:

```bash
bash scripts/install.sh --workspace /srv/r2d2 --prefix /opt/r2d2
```

### 2.1 Каталог сессий

```bash
mkdir -p "$HOME/r2d2-workspace"     # если не сделал scripts/install.sh
```

Сервер не создаёт его сам и не откажется: лаунчер проверяет и выходит с
ошибкой, если каталога нет. Путь в конфиге (`R2D2_WORKSPACE`) и путь в
`.env.oc` (`R2D2_OC_WORKSPACE`) должны совпадать.

### 2.2 Конфигурация R2D2 для opencode

```bash
bash scripts/install.sh              # или, только конфиг и шим:
bash scripts/install_r2d2_opencode_config.sh
```

Скрипт копирует `config/opencode/r2d2.opencode.json` в `~/.r2d2/opencode`
(каталог 0700, файл 0600) **байт в байт** и ставит шим в `~/.r2d2/r2d2_do.py`
(0755). Он **только пишет файлы** и ничего не запускает.

Два пути, почему так:

- **конфиг копируется дословно, а не «с подстановками».** Установленная копия
  обязана быть побайтово равна репозиторной: застрявшая старая копия продолжит
  действовать прежней матрицей разрешений, а это единственная защита R2D2
  (C2). Проверяет `tests/test_r2d2_opencode_config.py`. Поэтому пути в матрице
  записаны переносимо (`*/.r2d2/r2d2_do.py *`), а не абсолютными путями
  одной машины, — см. `config/opencode/README.md`.
- **шим — единственный отрисованный файл.** В нём `#!/…` и `VENV_PY = "…"`
  несут шаблон `@R2D2_REPO@`, и установщик подставляет в копию корень этого
  checkout. Абсолютный путь к интерпретатору в закоммиченном файле — это путь
  к чужой машине, и чем это кончалось, измерено: `os.execv` на отсутствующем
  интерпретаторе падает раньше любого обработчика, и агент получал трассировку
  в stderr и **пустоту** в stdout — единственный вывод, который он не умеет
  разбирать.

Копия, которую не подставили (запуск прямо из checkout или копирование руками),
находит свой venv сама, по `__file__`, и тоже переисполняется в него. Копия,
которой не нашлось venv, отвечает одной строкой JSON в stdout и кодом 1, а не
трассировкой.

> Почему нельзя просто положить конфиг в `~/.config/opencode/`: переменная
> `OPENCODE_CONFIG_DIR` **складывается** с глобальным конфигом, а не заменяет
> его. Свой каталог — это слой, а не изоляция, и собственные правила
> разрешений в нём обязаны быть строгими. Глобальный `opencode.json` при этом
> **не модифицируется** никогда.

### 2.3 `.env.oc` — пароль сервера

```bash
cp .env.oc.example .env.oc          # если не сделал scripts/install.sh
chmod 0600 .env.oc
openssl rand -base64 24             # → вставить в R2D2_OC_PASSWORD
```

`scripts/install.sh` создаёт `.env.oc` из примера, если его нет, и **никогда не
переписывает существующий**: второй запуск не способен стереть пароль.

systemd **не раскрывает** `${HOME}` в этом файле — значения читаются буквально.
`scripts/opencode_serve.sh` раскрывает сам все три домашних написания (`~`,
`$HOME`, `${HOME}`), поэтому значения из примера работают как есть; абсолютный
путь тоже работает — он нужен, если каталог сессий лежит вне `$HOME`.

`.env.oc` — живой файл с паролем, режим 0600 и в `.gitignore`. Обязательные
значения:

```dotenv
R2D2_OC_PORT=4599
R2D2_OC_USERNAME=opencode
R2D2_OC_PASSWORD=<сгенерированный пароль>
R2D2_OC_WORKSPACE=${HOME}/r2d2-workspace
# R2D2_OC_CONFIG_DIR=${HOME}/.r2d2/opencode
# R2D2_OC_BIN=${HOME}/.opencode/bin/opencode
```

**И то же самое в `.env` самого R2D2.** `R2D2_WORKSPACE` в `.env` обязан
называть тот же каталог: именно он уходит в сервер как `?directory=`, то есть
определяет, куда смотрят все сессии. Значение по умолчанию в `app/config.py` —
это путь одной машины (`/home/<user>/r2d2-workspace`), поэтому на другой машине
это обязательный шаг, а не украшение. Пока каталога нет, запросы честно
отказываются (`reason=workspace-missing`), а не работают не туда.

**`R2D2_OC_BIN` — закрепляет сборку opencode, но задавать его не обязательно.**
`scripts/opencode_serve.sh` разрешает бинарь в фиксированном порядке и никогда
не угадывает:

1. `R2D2_OC_BIN` — дословно, это единственный способ выбрать версию;
2. `~/.opencode/bin/opencode` — куда кладёт бинарь установочный скрипт opencode
   (шаг 0.1, вариант А), поэтому рекомендованный канал не требует ручного шага;
3. `PATH` — **только если там ровно один** исполняемый файл с именем `opencode`,
   и не молча: найденный абсолютный путь печатается в stderr, то есть в журнал
   systemd. Два кандидата и больше — **отказ** с перечислением обоих, а не выбор
   «какой первый». Один и тот же файл, видимый дважды (например `/bin` как
   симлинк на `/usr/bin`), считается одним: считаются файлы, а не пути.

Зачем отказ, а не выбор: «первый в `PATH`» — это ровно тот способ, которым
устаревшая копия забирает себе порт (шаг 0.1: три версии в трёх местах
одновременно). Лаунчер, который молча стартует не ту сборку, которую оператор
закрепил, хуже лаунчера, который отказался. Строка `exec` всегда использует
`"$BIN"`, то есть запускается именно разрешённый абсолютный путь.

**Пароль не может быть пустым.** `scripts/opencode_serve.sh` в этом случае
печатает объяснение и выходит с кодом 1, потому что opencode без
`OPENCODE_SERVER_PASSWORD` не предупреждает, а отвечает на все маршруты каждому
локальному процессу на машине. Пустая строка и строка из пробелов считаются
пустыми.

**Тот же пароль нужен R2D2 как клиенту.** В `config/backends.json` этот бэкенд
авторизуется как `${R2D2_OC_USERNAME}` / `${R2D2_OC_PASSWORD}`, и обе ссылки
подставляются из окружения самого R2D2, то есть из его `.env`. Значение в
`.env.oc` вооружает сервер; без него в `.env` бэкенд opencode выпадет из
реестра с WARNING, и маршрут работать не будет.

### 2.4 systemd-юнит пользователя

`scripts/r2d2-opencode.service` в репозитории — **шаблон**, а не готовый юнит.
Пути в нём записаны через `%h` — так systemd обозначает домашний каталог
пользователя, и это единственная переносимая запись: `${HOME}` в unit-файле
**не раскрывается**, и `systemd-analyze verify` отклоняет такой файл с «path is
not absolute» (проверено). Всё, что относится к checkout, в шаблоне указано для
той машины, на которой репозиторий писался, — поэтому копировать файл руками
имеет смысл, только если ваш checkout лежит там же.

Обычный путь — не копировать, а сгенерировать:

```bash
bash scripts/install.sh                        # шаг 2.0, пишет юнит с вашими путями
```

`--workspace DIR` переносит и `WorkingDirectory=` юнита, и `.env.oc`, и каталог
сессий разом, потому что все трое обязаны называть **один и тот же** каталог:
`systemd` делает `chdir` до `ExecStart`, а лаунчер потом делает свой `cd`.

Включение остаётся ручным и намеренным:

```bash
systemctl --user daemon-reload
systemctl --user enable --now r2d2-opencode
systemctl --user status r2d2-opencode
```

Юнит читает `EnvironmentFile=.env.oc` этого checkout, запускает
`scripts/opencode_serve.sh` и перезапускается через 3 с. Частота перезапусков
ограничена: без этого отказ лаунчера печатал бы своё объяснение каждые три
секунды вечно. Если юнит застрял в `failed` после исправления `.env.oc`:

```bash
systemctl --user reset-failed r2d2-opencode
systemctl --user start r2d2-opencode
```

Проверка:

```bash
curl -u opencode:"$R2D2_OC_PASSWORD" http://127.0.0.1:4599/global/health
# {"healthy":true,"version":"1.18.32"}
```

Отдельно стоит знать: отсутствующий `EnvironmentFile` юнита **не** считается
ошибкой (`systemd-analyze verify` это проверяет), а вот несуществующий
`ExecStart=` — считается, и юнит не стартует. Именно поэтому шаблон в
репозитории на чужой машине даст `verify` с кодом 1, а сгенерированный юнит
проходит его везде.

### 2.5. Модель в `config/backends.json` — обязательный шаг (C1)

**Это шаг, на котором останавливается машина без настроек.** `config/backends.json`
в репозитории — не абстракция, а слепок каталога моделей **одной** машины: во всех
трёх слотах там стоит `opencode/space-bunny-free`, потому что замер показал, что
все остальные бесплатные Zen-модели отвечают HTTP 200 с внутренним 403
`FreeTierError`, а платные — с внутренним 402 (замеры и выводы —
в [11-opencode-contract.md](11-opencode-contract.md)). На вашей машине opencode
предложит другой набор, и R2D2 об этом скажет.

Скажите, что именно предлагает ваш сервер:

```bash
curl -u opencode:"$R2D2_OC_PASSWORD" http://127.0.0.1:4599/config/providers
```

и поставьте id оттуда в три поля `opencode`-бэкенда в `config/backends.json`:

```json
"fast_model": "<provider>/<model>", "task_model": "<provider>/<model>",
"summarize_model": "<provider>/<model>"
```

**Почему это обязательный шаг, а не рекомендация.** Неизвестный `modelID` для
opencode — не ошибка: он подставляет другую модель, отвечает **200**, и ответ
выглядит как обычный. Никто ниже по цепочке этого не заметит (C1 в
[11-opencode-backend.md](11-opencode-backend.md)). Поэтому R2D2 проверяет все три
слота против `GET /config/providers` на старте и **отказывается поднимать
маршрут**, если хоть один не найден. Подставить другую модель молча — ровно та
поломка, ради которой эта проверка существует, поэтому отказ здесь оставлен
осознанно: ход уйдёт в цепочку фолбэков, а не в чужую модель.

Три разные причины отказа различаются намеренно (слово в скобках — это `reason`
в стартовой строке и в ответе `/diagnostics/providers`):

| `reason` | Что случилось | Что делать |
|---|---|---|
| `model-unknown` | сервер отвечает, но такого id в каталоге нет | взять id из `/config/providers` и вписать в `config/backends.json` |
| `model-unconfigured` | один из слотов пуст | заполнить все три слота |
| `catalogue-unreadable` | сам каталог прочитать не удалось | починить доступность `/config/providers`; модели тут ни при чём |
| `models-unverified` | сервер на старте не ответил | **это не отказ**: маршрут поднят, а `reachable` проверяется на каждом ходу |

## 3. Локальный запуск R2D2

```bash
cd R2_yandex_station
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env
# заполнить .env (шаг 5)

.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8080
```

Проверка:

```bash
curl http://127.0.0.1:8080/health
# {"status":"ok","opencode":{"reachable":true,"version":"1.18.32"},"sessions":0,"chain":["zen","yandexgpt","openrouter"]}
```

`reachable: false` — opencode-сервер не отвечает. Это **не поломка R2D2**:
процесс живет, `/health` отдаёт 200, и ходы уходят в цепочку фолбэков. Подробнее
о degraded-запуске — в разделе «Возможные проблемы».

Проверка webhook без туннеля (пример из [04-alice-protocol.md](04-alice-protocol.md)):

```bash
curl -X POST http://127.0.0.1:8080/webhook -H "Content-Type: application/json" -d '{
  "meta": {"locale":"ru-RU","interfaces":{}},
  "request": {"type":"SimpleUtterance","command":"привет"},
  "session": {
    "message_id":0,"session_id":"t1","skill_id":"<SKILL_ID>",
    "user":{"user_id":"<USER_ID>"},"application":{"application_id":"a1"},
    "new":true
  },
  "state":{}, "version":"1.0"}'
```

Живой каталог моделей и агентов:

```bash
curl -u opencode:"$R2D2_OC_PASSWORD" http://127.0.0.1:4599/config/providers
```

## 4. Публикация через cloudflared (HTTPS)

Алисе нужен публичный HTTPS-URL с валидным сертификатом. Используем cloudflared.

### Вариант А: быстрый туннель (для теста, URL меняется)

```bash
cloudflared tunnel --url http://127.0.0.1:8080
# → https://<random>.trycloudflare.com  (нужен каждый раз заново)
```

### Вариант Б: постоянный туннель (рекомендуется)

```bash
cloudflared tunnel login                          # откроется браузер, авторизация
cloudflared tunnel create r2d2                    # создаёт туннель с ID
cloudflared tunnel route dns r2d2 r2d2.example.com # свой домен на Cloudflare
```

`~/.cloudflared/config.yml`:

```yaml
tunnel: <TUNNEL_ID>
credentials-file: /home/<user>/.cloudflared/<TUNNEL_ID>.json
ingress:
  - hostname: r2d2.example.com
    service: http://127.0.0.1:8080
  - service: http_status:404
```

Запуск:

```bash
cloudflared tunnel run r2d2
# → https://r2d2.example.com отвечает, сертификат валиден
```

Проверить снаружи:

```bash
curl https://r2d2.example.com/health
```

> Если нет своего домена на Cloudflare — подойдёт вариант А, но URL меняется
> при каждом перезапуске, что неудобно для Endpoint в консоли Диалогов.

### Автозапуск R2D2 (systemd, опционально)

`~/.config/systemd/user/r2d2.service`:

```ini
[Unit]
Description=R2D2 server (the Alice skill)
After=network.target
Requires=r2d2-opencode.service

[Service]
WorkingDirectory=/home/<user>/R2_yandex_station
ExecStart=/home/<user>/R2_yandex_station/.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8080
Restart=always

[Install]
WantedBy=default.target
```

`Requires=` — не обязателен: R2D2 штатно работает без opencode (цепочка
фолбэков), и не поднимать его автоматически тоже правильно. Строка показана
потому, что порядок «мозг, потом шлюз» обычно удобнее.

Обратите внимание на bind: `127.0.0.1`, а не `0.0.0.0`. Наружу торчит только
туннель, поэтому порт R2D2 не должен быть доступен из локальной сети.

## 5. Переменные R2D2 (`.env`)

Полный актуальный список с комментариями — в `.env.example`. Минимально
необходимое:

```dotenv
# --- opencode-сервер (клиентская половина) ---
R2D2_OC_USERNAME=opencode
R2D2_OC_PASSWORD=<тот же пароль, что в .env.oc>
R2D2_BACKENDS_PATH=config/backends.json
R2D2_FAST_DEADLINE=3.2
R2D2_TASK_ACK=Проверяю, пришлю в телеграм.
R2D2_NEEDS_AGENT_SENTINEL=[[NEEDS_AGENT]]
R2D2_VOICE_AGENT=r2d2-voice
R2D2_TASK_AGENT=r2d2-agent
R2D2_WORKSPACE=/home/<user>/r2d2-workspace
R2D2_PERMISSION_TIMEOUT=300
R2D2_SESSION_SOFT_LIMIT=40
R2D2_STALE_SESSION_SECONDS=900
R2D2_CLI_PATH=/home/<user>/.r2d2/r2d2_do.py
R2D2_EVENT_POLL_INTERVAL=2.0

# --- цепочка фолбэков (необязательна) ---
R2D2_ZEN_KEY=<ключ Zen из ~/.local/share/opencode/auth.json, запись opencode>
OPENROUTER_API_KEY=sk-or-...
YANDEX_API_KEY=...
YANDEX_FOLDER_ID=...

# --- Telegram ---
TELEGRAM_BOT_TOKEN=
TELEGRAM_CHAT_ID=
# ОБЯЗАТЕЛЬНО, см. шаг 6.1: пары chat_id=application_id через запятую.
R2D2_TG_APPLICATION_ID=

# --- Алиса (whitelist) ---
# Пустые значения означают ЗАКРЫТЫЙ webhook: /webhook отвечает 403 каждому.
ALICE_SKILL_ID=
ALICE_USER_ID=
# Только для разработки, до регистрации навыка. Держать порт на loopback.
R2D2_ALLOW_UNAUTHENTICATED=

# --- прочее ---
SERVER_HOST=127.0.0.1
SERVER_PORT=8080
DB_PATH=db/sessions.db
SHELL_ENABLED=true
SHELL_TIMEOUT_SECONDS=10
```

### 5.1 `R2D2_ZEN_KEY` — что это и когда нужен

Это ключ из записи `opencode` в `~/.local/share/opencode/auth.json` (либо из
консоли Zen). В `config/backends.json` он подставляется как `${R2D2_ZEN_KEY}` в
поле `api_key` бэкенда `zen` и нужен **только цепочке фолбэков** — сам
opencode-маршрут ходит в opencode под учёткой сервера, и этот ключ его не
касается.

Практически: если Zen не пополнен, фолбэк на `zen` вернёт отказ по балансу и
ход уйдёт дальше по цепочке. Это не поломка, но и не польза, поэтому при
непополненном балансе честнее оставить поле пустым — бэкенд выпадет из цепочки
с WARNING, и в логе будет видно, что он не причина отказа.

Документация и примеры используют только плейсхолдеры вида `${ИМЯ_ПЕРЕМЕННОЙ}`.
Реальные значения живут в `.env` и `.env.oc`, оба в `.gitignore`.

## 6. Telegram-бот

1. В Telegram → `@BotFather` → `/newbot` → имя `R2D2_Butler` → получаешь токен.
2. Узнать свой `chat_id`: написать боту `/start`, затем
   `curl https://api.telegram.org/bot<TOKEN>/getUpdates` → `chat.id`.
3. Прописать в `.env`: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`.
4. Опционально поставить webhook для бота:
   `https://api.telegram.org/bot<TOKEN>/setWebhook?url=https://r2d2.example.com/tg/webhook`

Telegram — единственный канал, который умеет **доставлять**: Алиса не может
прислать ответ позже. Поэтому через него приходят и длинные результаты, и
вопросы о подтверждении команд.

### 6.1. `R2D2_TG_APPLICATION_ID` — обязательный шаг, без него Telegram молчит

**Это тот же класс шага, что 2.5, и по той же причине.** Алиса не умеет ждать и
присылать позже: длинный результат агента и вопрос «разрешить выполнить
команду?» идут в Telegram. Если чат не объявлен, `/tg/webhook` **молча
отбрасывает** каждое сообщение, ответ `да` в Telegram не доходит до сессии, в
которой вопрос был задан, и брокер разрешений умирает на 300-й секунде, отклонив
вопрос. Ничего не взламывается и ничего не отвечает не тому — просто проект
работает наполовину, и это нигде не видно.

Идентичность **объявляется, а не выводится** из `chat_id`. Придумывать её нельзя:
один человек — это одна сессия opencode и один ожидающий вопрос, и две разные
идентичности для одного человека дают «да», доставленное не туда.

Формат — пары `chat_id=application_id`, разделённые запятой или пробелом:

```dotenv
# ваш TELEGRAM_CHAT_ID  =  application_id, который присылает Алиса
R2D2_TG_APPLICATION_ID=123456789=aa11bb22-cc33-dd44-ee55-ff6677889900
```

`application_id` берётся из тела запроса Алисы — из сессии, к которой уже
привязан навык (тот же, что в `ALICE_SKILL_ID`/`ALICE_USER_ID` по смыслу, но это
**другае** пара: `application_id` у Алисы и `user_id` — разные значения).
Второй чат добавляется второй парой, а не придумыванием:

```dotenv
R2D2_TG_APPLICATION_ID=123456789=aa11...9900,987654321=ff00ee11-dd22-cc33-bb44-aa5544332211
```

Токен, который не читается как такая пара, **ничего не связывает** и
предупреждает в логе: одна опечатка не может выглядеть как объявление.

Проверка:

```bash
curl http://127.0.0.1:8080/diagnostics/providers | python3 -m json.tool | grep -A3 telegram
# "telegram": {"declared": true, "variable": "R2D2_TG_APPLICATION_ID",
#              "format": "chat_id=application_id"}
```

`declared: false` — привязки нет, и Telegram сейчас не отвечает. В стартовой
строке это же видно полем `telegram=unbound` плюс отдельное WARNING с именем
переменной.

## 7. Настройка навыка в Яндекс.Диалогах (ручной шаг)

Этот шаг **не автоматизируется** — навык регистрируется в консоли вручную.

1. Открой [dialogs.yandex.ru](https://dialogs.yandex.ru/) → «Создать диалог» →
   тип «Навык Алисы».
2. **Общие сведения:**
   - Название: `Р2Д2` (2–5 слов; одно слово допустимо для уникального бренда).
   - Активационные имена: пробуем `Р2Д2`, `Р2`, `Р-два-дэ-дэ`. Если
     короткие латинские не принимаются (мин. длина), оставляем только валидные
     (см. [02-alice-requirements.md](02-alice-requirements.md)).
   - Иконка: любая картинка (для приватного не критично).
3. **Backend:**
   - Endpoint URL: `https://r2d2.example.com/webhook` (проверка «Проверить»
     пройдёт, если сервер отвечает).
4. **Доступ:**
   - Тип доступа: **«Приватный»** (только для тебя). Автомодерация быстрая.
5. **Проверка голосом:**
   - Убедись, что на Станции и в телефоне залогинен тот же Яндекс-аккаунт.
   - Скажи: «Алиса, запусти навык Р2Д2», затем «Р2, привет», «Р2, что ты умеешь».
6. Если хочешь в каталог (не обязательно) — смени доступ на «Публичный» и
   пройди полную модерацию (до 3 дней).

> `ALICE_SKILL_ID` и `ALICE_USER_ID` из консоли копируются в `.env` вручную.
> Пока они пустые, whitelist не срабатывает — см. [09-security.md](09-security.md).

## 9. Возможные проблемы

| Проблема | Решение |
|---|---|
| `opencode_serve.sh: … is missing or not executable` | Не задан `R2D2_OC_BIN` в `.env.oc`, или путь не тот (шаг 0.1, 2.3) |
| `opencode: server unreachable` в логе | `systemctl --user status r2d2-opencode`; чаще всего пустой `R2D2_OC_PASSWORD` или отсутствующий `~/.r2d2/opencode` |
| Юнит `r2d2-opencode` в `failed` | `journalctl --user -u r2d2-opencode`; после исправления `.env.oc` — `systemctl --user reset-failed r2d2-opencode` |
| `opencode=wired, models=unverified, reason=models-unverified` при старте | Сервер не ответил на старте; маршрут поднят, но модели не проверены. Проверить `curl -u opencode:… /config/providers` |
| `the brain route is NOT wired [model-unknown]` | Шаг 2.5: в каталоге вашего сервера нет модели, указанной в `config/backends.json`. Это слепок чужой машины, а не поломка |
| `the brain route is NOT wired [model-unconfigured]` | Пустой один из трёх слотов модели |
| `the brain route is NOT wired [catalogue-unreadable]` | Не читается `/config/providers`; про сами модели ничего не известно — чинить доступность, а не конфиг |
| `fallback=[]` при старте | Ни один бэкенд цепочки не собран: у всех пустые ключи. WARNING от `build_chain` называет поле. Без opencode-маршрута отвечать тогда нечем |
| `backend 'opencode' … dropped from the chain, 'password' is empty` | `R2D2_OC_PASSWORD` не в `.env` R2D2 (только в `.env.oc`) |
| В логе `telegram: R2D2_TG_APPLICATION_ID is empty` | Шаг 6.1: чат не привязан, Telegram не отвечает. Ничего не сломано — просто не объявлено |
| В логе `chat … is not bound to an application_id` | В `R2D2_TG_APPLICATION_ID` нет пары с этим `chat_id`; идентичность не выдумывается намеренно |
| `GET /config/providers does not list fast_model=…` | Модель недоступна на этой машине; см. [11-opencode-backend.md](11-opencode-backend.md), C1 |
| «Некорректный SSL-сертификат» | Использовать cloudflared/ngrok, не самоподписанный cert |
| Навык «не отвечает», в логе 403 | Не заданы `ALICE_SKILL_ID`/`ALICE_USER_ID`: webhook закрыт. Для локальной проверки — `R2D2_ALLOW_UNAUTHENTICATED=1` на loopback |
| Активационное имя не распознаётся | Пробовать другие варианты; выдуманным словам нужно «обучение» (недели) |
| Не приходят сообщения в ТГ | Проверить `TELEGRAM_BOT_TOKEN`/`CHAT_ID`, webhook, доступ к api.telegram.org |
| Ответ из opencode всегда идёт в ТГ | Сессия холодная: первый ход стоит 15.5–18.6 с и всегда уходит агенту. Второй ход уже голосом |
