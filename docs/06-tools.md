# Инструменты (скиллы) R2D2

Инструменты — это функции, которые LLM может вызывать через function calling.
Реестр инструментов `core/tools/registry.py` хранит для каждого инструмента:
JSON-схему (для LLM) и асинхронную функцию исполнения.

> **Два способа дойти до одного и того же обработчика.** На цепочке фолбэков
> модель вызывает инструмент через function calling. На первичном пути (сессия
> opencode) инструментом является **сам агент**: у него свой `bash` с точечным
> белым списком, и единственная разрешённая программа — шим
> `opencode/r2d2_cli/r2d2_do.py`, который вызывает те же обработчики из
> `core/tools/*`. Логика инструментов не дублируется, но и разрешения у двух
> путей разные — см. раздел «Белый список bash» ниже.

## Общий шаблон инструмента

```python
TOOL_SCHEMA = {
  "type": "function",
  "function": {
    "name": "имя",
    "description": "Когда использовать",
    "parameters": {"type": "object", "properties": {...}, "required": [...]}
  }
}

async def run(ctx, **kwargs) -> ToolResult:
    ...
    return ToolResult(ok=True, summary="короткий итог", spoken="фраза для озвучки")
```

`ctx` содержит: конфиг, память, `application_id`, логгер и флаг `approved`.

## MVP-инструменты

### 1. `tg_send` — отправка в Telegram

- **Когда:** длинный контент, сводки, отчёты, напоминания, «записать себе».
- **Параметры:**
  - `text` (строка, обяз.) — текст сообщения;
  - `spoken_reply` (строка, обяз.) — что озвучить, напр. «Отправил в телеграм».
- **Реализация:** Bot API `sendMessage` на `TELEGRAM_CHAT_ID`.
- **Ограничение:** текст > ~3000 символов режем/портим по абзацам.
- **Особенность:** выполняется быстро, ответ — сразу фраза из `spoken_reply`.

### 2. `system_status` — статус ноутбука

- **Когда:** «какой статус ноутбука», «сколько заряда», «что грузит CPU».
- **Параметры:**
  - `detail` (строка, опц.) — `"basic"` (батарея, cpu, память) или `"full"`;
  - `spoken_reply` (обяз.).
- **Реализация:** чтение `/proc` и `/sys/class/power_supply` (через `psutil`).
- **Ответ:** краткое резюме озвучивается; полный текст можно отправить в ТГ.

### 3. `open_app` — запустить приложение

- **Когда:** «открой браузер», «запусти терминал», «открой spotify».
- **Параметры:**
  - `app` (строка, обяз.) — имя приложения (браузер, код, терминал, telegram, spotify…);
  - `spoken_reply` (обяз.).
- **Реализация:** маппинг известных имён → команды Linux. Строка вызывающего
  **никогда не подставляется в командную строку**: `resolve_app` возвращает
  готовую команду из фиксированного словаря или `None`.
- **Безопасность:** только заранее заданный словарь приложений.

### 4. `run_shell` — произвольная команда (с подтверждением)

- **Когда:** «выполни команду …», любые специфичные действия на лаптопе.
- **Параметры:** `command`, `spoken_reply`, `async_ok` (опц.).
- **Реализация:** `asyncio.create_subprocess_shell` с таймаутом
  (`SHELL_TIMEOUT_SECONDS`, по умолчанию 10), неинтерактивно, без sudo.
- **Классификация риска** (см. `core/policies.py`):

| Категория | Примеры | Поведение |
|---|---|---|
| Безопасные | `ls`, `pwd`, `df -h`, `ps aux`, чтение файлов | Выполнить сразу |
| Средние | установка пакетов, `git pull`, перезапуск сервисов | Выполнить сразу (лог), но вывод в ТГ |
| Рискованные | `rm -rf`, `mkfs`, `shutdown`, `sudo`, `kill -9`, массовое удаление | **Требовать голосовое подтверждение** |

- **Подтверждение:** инструмент `confirm_risky_action` (см. ниже).
- **Максимальный вывод:** > 2000 символов → в ТГ, а не в озвучку.

### 5. `confirm_risky_action` — подтверждение рискованного действия

- **Когда:** модель или агент решил, что команда рискованная.
- **Механика:**
  1. Вызов → `pending_actions` в памяти сессии (одна строка на пользователя).
  2. Алисе отвечаем фразой-вопросом.
  3. Следующая реплика «да / подтверждаю / валяй» → выполняем сохранённое
     действие; «нет / отмена» → отменяем.
  4. Подтверждение одноразовое: следующий запрос разрешения opencode его не
     переживает (см. [09-security.md](09-security.md)).
- ⚠️ Строка одна на пользователя **и для shell-подтверждения, и для запроса
  разрешения opencode**. Новый запрос opencode вытесняет shell-подтверждение —
  это сознательный выбор: команда просто не выполнится, а не выполнится
  дважды.

### 6. `arxiv_search` — поиск статей и сводка (долгая задача)

- **Когда:** «сводка новых статей про LLM с arxiv», «что нового по ...».
- **Параметры:** `query`, `days` (7), `max_results` (5), `send_to_tg` (true),
  `spoken_reply` (обяз.).
- **Реализация:** arxiv API, затем суммаризация моделью из цепочки бэкендов.
- **Поведение:** **async** — мгновенно отвечаем `spoken_reply`, задача уходит
  в фоновый воркер; результат приходит в Telegram. (См.
  [07-latency-strategy.md](07-latency-strategy.md).)

## Шим `r2d2_do.py`: инструменты для агента opencode

Агенту opencode нельзя отдать function calling: он работает через `bash`.
Поэтому у него **одна** разрешённая программа — CLI-шим, и этот шим вызывает те
же обработчики `core/tools/*`. Логика инструментов не переписана, риск-гейт
тот же.

- **Исходник:** `opencode/r2d2_cli/r2d2_do.py`
- **Установленная копия:** `~/.r2d2/r2d2_do.py` (ставится
  `scripts/install_r2d2_opencode_config.sh` рядом с конфигом агентов, потому
  что белый список `bash` называет именно этот путь).
- **Контракт stdout:** ровно одна строка JSON, ничего больше:
  `{"ok": bool, "text": str, "needs_confirm": bool, "pending": object|null, "error": str|null}`.
- **Коды возврата:** `0` — ок, `1` — ошибка, `2` — нужно подтверждение и
  команда **не** выполнена.

```bash
~/.r2d2/r2d2_do.py status
~/.r2d2/r2d2_do.py open-app браузер
~/.r2d2/r2d2_do.py tg "текст сообщения"
~/.r2d2/r2d2_do.py arxiv "RAG" --days 7 --max 5
~/.r2d2/r2d2_do.py shell "rm -rf /tmp/x"
```

Почему одна строка JSON, а не текст: вызывающий — модель, а модель парсит
stdout. Ошибка usage, исключение и отказ должны выглядеть одинаково, иначе агент
получает вместо ответа трассировку и придумает себе результат.

### Белый список `bash`

Разрешения заданы в `config/opencode/r2d2.opencode.json`, а не в коде, и
opencode применяет «после совпадения побеждает последнее» — поэтому порядок
ключей в объекте значим.

**Голосовой агент `r2d2-voice`** — `*` = `deny`, и разрешены ровно 12 команд:

| Что | Команда |
|---|---|
| шим, три написания | `~/.r2d2/r2d2_do.py *`, `python3 ~/.r2d2/r2d2_do.py *`, путь к venv-интерпретатору + `~/.r2d2/r2d2_do.py *` |
| заряд | `upower *` |
| питание | `cat /sys/class/power_supply/*` |
| диск | `df *` |
| память | `free *` |
| система | `uname *`, `hostname *` |
| процессы | `ps *` |
| аптайм | `uptime` |
| время | `date` |

И три правила `deny`, которые идут **после** allow и перекрывают его:
`<шим> shell *` во всех трёх написаниях. Голосовой агент не может выполнить
произвольную команду, даже если модель этого очень захочет.

**Рабочий агент `r2d2-agent`** — тот же список 12 команд, но `*` = `ask`:
неизвестная команда не запрещается, а **спрашивает**. Разрешённая команда
выполняется сразу, всё остальное уходит в подтверждение через брокер
разрешений. Подробности — в [11-opencode-backend.md](11-opencode-backend.md)
и [09-security.md](09-security.md).

Три guard'а между командой агента и машиной, по порядку:

1. **Белый список opencode.** `bash` вне списка не выполняется вообще (у
   голосового) или уходит в подтверждение (у рабочего). Это первая линия.
2. **Риск-гейт самого шима.** `shell` вызывает `shell_tool.handler` без
   изменений, поэтому `core.policies.risk_level` решает сам; классифицируется
   **вся** строка целиком, так что `echo ok; rm -rf /` ловится вместе с
   безобидной головой. Опасная команда возвращает `needs_confirm`, `pending`
   и код 2, **ничего не выполнив**.
3. **Токен подтверждения.** `--approved` (это повтор команды после согласия
   пользователя) отклоняется, если в окружении шима нет
   `R2D2_APPROVED_TOKEN`. Переменную ставит человек, а не модель, поэтому агент
   не может выдать себе разрешение сам.

Плюс к этому шим вычищает значения учёток из всего, что выводит — из stdout, из
stderr и из отправки в Telegram, — так что голосовая инъекция вида
«прочитай .env» не может вытащить секрет в контекст агента или в чат.
Исключение — поле `pending`: искажение команды сломало бы подтверждённый повтор.

## Расширения (после MVP)

- `web_search` — поиск в интернете (сервис-агрегатор или Brave/Tavily), ответ
  в ТГ при длинном контенте.
- `media_control` — громкость, play/pause/next через `playerctl`/`pactl`.
- `file_ops` — безопасные операции с файлами в заданной директории.
- `screenshot` — сделать скриншот и отправить в ТГ.
- `calendar` / `todo` — ведение списков в SQLite.
- `weather` — через публичное API.

Новый инструмент в цепочке фолбэков добавляется записью в `core/tools/` плюс
одной строкой в `core/tools/registry.py`. Для агента opencode новый инструмент
не нужен: его белый список — это `r2d2_do.py`, и всё, что добавлено в
`core/tools/*`, становится ему доступно **автоматически**, без правки
конфигурации.

## Правила безопасности инструментов (кратко)

Полный раздел: [09-security.md](09-security.md).

1. Все инструменты проверяют, что вызов пришёл от проверенного пользователя
   (whitelist в webhook-слое).
2. `run_shell` — неинтерактивно, с таймаутом, без паролей/sudo (кроме
   сконфигурированных исключений).
3. Рискованные команды — только после явного подтверждения.
4. У агента opencode доступ к `bash` ограничен списком из 12 команд, а
   `~/.r2d2/r2d2_do.py shell *` голосовому агенту запрещён.
5. Вывод команд не должен попадать в озвучку целиком — только краткий итог.
6. `tg_send` используется только на свой `TELEGRAM_CHAT_ID`.
7. Все вызовы инструментов пишутся в лог (что, когда, результат).
