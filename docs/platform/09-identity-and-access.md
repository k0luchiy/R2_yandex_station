# Идентификаторы, OAuth, состояние

Три идентификатора, на которых держится любое состояние диалога, и связка аккаунтов.

## Три идентификатора

```json
"session": {
  "session_id": "2eac4854-fce721f3-b845abba-20d60",
  "message_id": 4,
  "skill_id": "<ваш навык>",
  "user": {
    "user_id": "<пользователь в паре навык-пользователь>",
    "access_token": "<если есть связка аккаунтов>"
  },
  "application": {
    "application_id": "<экземпляр приложения в паре навык-приложение>"
  },
  "new": false
}
```

| Поле | Что это | Стабильность |
|---|---|---|
| `session.skill_id` | ваш навык | вечно |
| `session.session_id` | один разговор | **умирает вместе с сессией** |
| `session.message_id` | номер хода | растёт на каждом запросе |
| `session.user.user_id` | человек | постоянный |
| `session.application.application_id` | экземпляр приложения | постоянный |
| `session.user_id` верхнего уровня | устарело | **не поддерживается** |

### `session.user_id` не поддерживается

Прямая формулировка документации:

> Свойство не поддерживается — вместо него следует использовать новое, полностью аналогичное
> свойство `session.application.application_id`.

При этом в примерах документации поле **присутствует**, с тем же значением, что
`application.application_id`. То есть на проводе оно есть, поддержки нет. **Не читайте его.**

### `application_id` — не «приложение, где говорит пользователь»

> Идентификатор экземпляра приложения, в котором пользователь общается с Алисой […] Даже если
> пользователь вошел в один и тот же аккаунт в приложение Яндекс для Android и iOS, Яндекс Диалоги
> присвоят **отдельный `application_id` каждому из этих приложений**.

И второе, более важное ограничение:

> Этот идентификатор уникален для пары **«приложение — навык»**: в разных навыках значение
> свойства `application_id` для одного и того же пользователя будет различаться.

**Практический вывод для R2D2.** `application_id` различается между телефоном и Станцией. Один и
тот же человек на двух устройствах получит **две разные сессии opencode** и два разных ожидающих
вопроса подтверждения. Это не баг, а следствие определения.

Если для проекта критично, чтобы голос на Станции и текст в Telegram принадлежали **одной**
сессии opencode, ключ надо строить на `session.user.user_id` — он единственный общий для всех
устройств.

### `session.user.user_id` — пара «пользователь — навык»

> Идентификатор пользователя Яндекса, единый для всех приложений и устройств. Этот идентификатор
> уникален для пары **«пользователь — навык»**: в разных навыках значение свойства `user_id` для
> одного и того же пользователя будет различаться.

Два свойства сразу:

- **единый для всех устройств** — годится как ключ памяти человека;
- **уникален внутри навыка** — значение нельзя использовать как глобальный идентификатор Яндекса
  и нельзя сопоставлять между двумя навыками.

Конструкция совпадает с `psuid` у Яндекс ID: пара `client_id` + `user_id`. Это скорее плюс:
значение непрозрачно и не раскрывает внутренний идентификатор аккаунта.

### Когда `session.user` отсутствует

> Атрибуты пользователя Яндекса, который взаимодействует с навыком. **Если пользователь не
> авторизован в приложении, свойства `user` в запросе не будет.**

Значит `session.user` может не быть вообще. Любой разбор обязан это переживать:

```python
session = body.get("session", {})
user_id = (session.get("user") or {}).get("user_id")   # None, если не авторизован
```

Именно так и сделано в `core/brain.py`.

## Какой идентификатор для чего

| Задача | Поле |
|---|---|
| whitelist «это мой пользователь?» | `session.user.user_id` |
| память диалога, общая для всех устройств | `session.user.user_id` |
| память, привязанная к устройству | `session.application.application_id` |
| рамка одного разговора | `session.session_id` — **только** на время сессии |
| сопоставить пользователя между двумя навыками | **невозможно** этими полями |

Каноническая стратегия из поддерживаемой библиотеки `aliceio`:

```python
user_id = user.user_id if user else session.application.application_id
```

с пояснением в исходнике: если стратегия по `user_id`, то у пользователя без аккаунта состояние
будет по устройству, а у авторизованного — везде и всегда. То есть **два уровня памяти**: общий
для авторизованного, локальный для анонимного.

## Время жизни сессии

> Сессия — это период относительно непрерывного взаимодействия пользователя с навыком.

Сессия завершается, когда:

- пользователь выходит из навыка;
- навык отвечает `"end_session": true`;
- пользователь долго не даёт команд — **тайм-аут зависит от поверхности, минимум несколько минут**.

Следствие: `session_id` **не годится** как долговременный ключ. Он умирает вместе с сессией.

## Связка аккаунтов (OAuth)

### Когда она нужна

Навыку, который обращается к внешнему сервису от имени пользователя. Навыки Умного дома
**всегда** требуют связки — пользователь не может начать работу, пока не свяжет аккаунт.

### Поля в консоли

Вкладка «Связка аккаунтов»:

| Поле | Что вписать |
|---|---|
| Идентификатор приложения | `client_id` **вашего** OAuth-приложения на **вашем** сервере авторизации |
| Секрет приложения | секрет того же приложения |
| URL авторизации | адрес страницы входа |
| URL для получения токена | адрес обмена кода на токен |
| URL для обновления токена | адрес обновления |
| Идентификатор группы действий | scope, например `home:lights` |

Важно: `client_id` — это **не** идентификатор навыка и **не** `application_id`. Это отдельная
сущность.

`redirect_uri` **фиксирован** и не настраивается:

```
https://social.yandex.net/broker/redirect
```

### Ограничения

| Параметр | Значение |
|---|---|
| Длина ответа токена | 5000 символов |
| Длина `access_token` и `refresh_token` | по **2048** символов |
| `expires_in` | целое от 1 до 4 294 967 296 |
| Время на ответ сервера токенов | **5 секунд** |

Допускается **только** authorization code grant. Implicit и password-flow не принимаются.

> Если через 5 секунд Диалоги снова не получат ответ, **связка аккаунтов будет разорвана**.

Разрыв происходит после **двух** подряд неудачных попыток. Значит на сервере токенов нужен
запас по времени: две неудачи подряд — и пользователю придётся авторизовываться заново.

### Где смотреть доступные права

`https://oauth.yandex.com/client/<client_id>/info` — страница со списком прав приложения.

Права Яндекс ID: `login:info`, `login:email`, `login:avatar`, телефон, дата рождения. **Ни**
календарей, **ни** музыки, **ни** заметок. Навык не получает доступ к пользовательским данным
автоматически — только то, что запрашивается через OAuth и разрешено пользователем.

### Токен в запросе

`session.user.access_token` приходит в каждом запросе при настроенной связке **и** дублируется в
заголовке `Authorization`. Это токен **вашего** ресурсного сервера, полученный Яндексом по
authorization code. Не путайте его с токеном Яндекс ID.

**Проверяйте токен.** Документация требует этого, и это единственная защита эндпоинта: без
связки аккаунтов любой может обратиться к вашему вебхуку.

## Три механизма состояния

```json
{
  "session_state":       { },
  "user_state_update":   { },
  "application_state":   { }
}
```

| Механизм | Область | Квота |
|---|---|---|
| `session_state` | в пределах сессии | **1 КБ** |
| `user_state_update` | пользователь Яндекса | **1 КБ** |
| `application_state` | экземпляр приложения | **1 КБ** |

В запросе то же самое приходит в `state`:

```json
"state": { "session": {}, "user": {}, "application": {} }
```

Появляется, только если в консоли включено «Использовать хранилище данных в навыке».

⚠️ **Репозиторий `vksdk` содержит «5 КБ» для `user_state_update`.** Это ограничение **Маруси**,
а не Алисы: в `vksdk` каталог `marusia/` — отдельный ассистент VK. Не берите это число для Алисы.

## Политика конфиденциальности

**Отдельного поля в консоли навыка нет.** Полный перечень полей навыка его не содержит.

Требование при этом юридическое:

> **3.10.** Разработчик перед началом взаимодействия с Пользователем должен предоставить ему
> доступным способом полную юридически значимую информацию… **Политику Конфиденциальности**… Яндекс
> оставляет за собой право затребовать соответствующие документы в рамках модерации.

На практике ссылку размещают в описании навыка либо в поле «Сайт». Модерация может потребовать
документ отдельно — это право, а не автоматическая проверка.

## Ответы на частые вопросы

**`user_id` — это на аккаунт или на навык?**
На пару. Он постоянен для пользователя **внутри одного навыка** и различается в разных навыках.

**Можно ли сопоставить пользователя между своим навыком и, скажем, телеграм-чатом?**
Только если вы сами объявили связь. Документация не даёт никакого идентификатора, обходящегося
этими полями.

**`application_id` переживает перезапуск навыка?**
Да, он привязан к экземпляру приложения, а не к процессу навыка.

**Анонимный пользователь — что доступно?**
Только `application_id`. Ни `user`, ни `access_token`, ни `user_state_update` для него не будет.
