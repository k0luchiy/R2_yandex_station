# Ошибки и отладка

Что делает платформа, когда навык ломается, и как это диагностировать. Ориентироваться стоит на
плохое сообщение: **платформа почти ничего не сообщает разработчику сама**.

## Что видит пользователь

| Ситуация | Что говорит Алиса |
|---|---|
| вебхук не ответил за 4,5 с | «навык не отвечает» |
| ответ не соответствует формату | сообщение о том, что навык не отвечает |
| вебхук вернул 5xx | то же |

Сессия при этом **закрывается**. Не «попробуйте ещё раз», а конец.

Дальше пользователь говорит «Алиса, вернись» и пробует снова — если повезёт со второй попыткой.

## Почему это трудно

Три вещи, которые делают отладку навыка неудобной:

1. **Логов платформы у вас нет.** У Яндекса нет ваших логов; всё, что вы можете, — записать
   самостоятельно на своей стороне.
2. **Ответ может пройти и всё равно не сработать.** 200 с валидным JSON, но без `end_session`
   — сессия закрывается как «неполный ответ».
3. **Часть отказов молчаливая.** Превышение лимита в 5000 символов, слишком много кнопок,
   недоступная картинка — могут не дать видимой ошибки.

Поэтому единственный надёжный метод — **записать входящий запрос целиком и воспроизвести его
локально**.

## Инструменты консоли

### Тестер

Вкладка «Тестирование»: слева переписка с Алисй, справа — сырые JSON запроса и ответа.

Переключатели:

| Переключатель | Что делает |
|---|---|
| **Нет экрана** | имитирует устройство без экрана — например, Станцию Мини |
| **Анонимный пользователь** | проверка поведения без авторизации |

Ограничения, которые надо знать:

> При тестировании в консоли разработчика навык считается постоянно активированным, поэтому
> проверить работу активационных имен здесь нельзя.

И ещё: отображение в тестере — **приблизительное**, не такое, как на устройстве.

Тестер бьёт по **вашему настоящему адресу**. Это не «пробный» сервер: запрос уходит на
продакшн-вебхук, со всеми его побочными эффектами.

### Мониторинг

Вкладка «Мониторинг», **только для опубликованных навыков**:

- **Запросы в навык** — средний RPS, типы ошибок, их количество и доля, включая `error_http_5xx`;
- **Тайминги** — перцентили задержки.

Глубина истории — до шести месяцев. Источник запросов: «Пользовательские запросы».

**Ключевая метрика модерации** видна здесь же: не более **одной ошибки сервера на
10 обращений**. Эта цифра — не рекомендация, а порог, за которым навык отключают.

### Проверка живости

`original_utterance: "ping"` — служебный запрос платформы. Обрабатывайте его **до** бизнес-логики,
иначе навык попытается ответить на «пинг» как на запрос пользователя.

У R2D2 для этого есть `/health`, но `ping` от платформы и локальный `/health` — разные вещи:
`ping` приходит на `/webhook` и должен быть обработан там.

## Симптом → причина

### «Алиса говорит, что навык не отвечает»

| Проверить | Как |
|---|---|
| Замерьте время от отправки запроса до **полного** получения ответа | Не до первого байта. Стриминг не помогает |
| Не холодный ли старт | Первый запрос после простоя — самый долгий |
| Не упирается ли процесс в DNS или TLS | Рукопожатие до дальнего адреса — 150–400 мс |
| Не блокирует ли работа в цикле событий | `async` вместо блокирующих вызовов |
| Для навыка Умного дома — не 3 ли секунды вместо 4,5 | Свой бюджет |

### «Работает локально, не работает через туннель»

| Проверить | Как |
|---|---|
| Адрес в консоли совпадает с тем, что отдаёт туннель сейчас | Консоль хранит **строку**, не DNS |
| Тоннель не сменил имя при перезапуске | У быстрых туннелей меняется всегда |
| Адрес доступен **извне**, а не с localhost | Проверьте с чужой сети |
| Статус ответа ровно `200`, а не `302` | Редиректы могут не следоваться |

### «Сессия закрывается после первого ответа»

Почти всегда — отсутствие `end_session`:

```json
{ "response": { "text": "…", "end_session": false }, "version": "1.0" }
```

`end_session` обязателен **даже если `false`**. Забытое поле закрывает сессию как «ответ не
соответствует формату».

### «Иногда отвечает, иногда нет»

| Проверить | Как |
|---|---|
| Ошибка в ветке, которая не отдаёт ответ | Любой необработанный exception должен давать `200` с текстом |
| Запрос без `session.user` | Анонимный пользователь — `session.user` отсутствует |
| `request.command` пуст | Первый контакт и `ButtonPressed` дают пустую команду |
| Превышен лимит ответа | Считайте длину **всего** тела, не только `text` |

### «Изображение не показывается»

Сначала проверьте поверхность: возможно, это Станция, и картинка не покажется **в принципе**.
Подробно — [05-station-and-activation.md](05-station-and-activation.md).

Если поверхность с экраном:

| Проверить | Как |
|---|---|
| Картинка загружена, а не по URL | `card.image.url` не существует |
| `image_id` корректный | Формат `<skill-id или user-id>/<хэш>` |
| Размер в допуске | 1 КБ – 1 МБ |
| Формат поддерживается | PNG, JPEG, GIF, BMP, TIFF, WEBP |
| Квота не исчерпана | 100 МБ на аккаунт, при превышении — `429` |

### «Навык не слышат»

| Проверить | Как |
|---|---|
| Время обучения нового слова | 2–3 недели после публикации |
| Падеж в активационном имени | «запусти Игру» и «запусти Игру Нубик» — разные команды |
| Название не слишком общее | Схожие названия запрещены |
| Навык опубликован, если приватный | Голосом вызывается опубликованный приватный навык |
| Станция авторизована под тем же аккаунтом | Иначе приватный навык не виден |

### «Всё работало и перестало»

| Проверить | Как |
|---|---|
| Адрес изменился | Самая частая причина |
| Истёк dev-домен туннеля | ngrok и подобные |
| Сертификат просрочен | Let’s Encrypt — 90 дней |
| Навык отключён за недоступность | Проверьте вкладку «Мониторинг» |
| Навык отклонён при повторной модерации | Старая версия продолжает работать, но настройки могли поменяться |

## Что отвечать при ошибке

**Всегда `200`, даже при внутренней ошибке:**

```python
try:
    text = do_work()
except Exception:
    logger.exception("handle failed")
    text = "Что-то пошло не так, попробуйте ещё раз."

return JSONResponse(
    {"response": {"text": text, "end_session": False}, "version": "1.0"}
)
```

Причина не только в сообщении: 5xx стоит в счёт **одной ошибки из десяти**, после которых
навык отключают. Собственный текст об ошибке в 200 — это и пользователю полезно, и статистику
не портит.

## Как отлаживать правильно

### Записать и воспроизвести

Единственный метод, который работает без доступа к платформенным логам:

```python
@app.post("/webhook")
async def webhook(request: Request) -> JSONResponse:
    body = await request.json()
    logger.info("alice request: %s", json.dumps(body, ensure_ascii=False))
    started = time.monotonic()
    response = await handle(body)
    elapsed = time.monotonic() - started
    logger.info("alice response in %.3fs: %s", elapsed, json.dumps(response, ensure_ascii=False))
    return JSONResponse(response)
```

Затем этот же JSON отправляете локально:

```bash
curl -X POST http://127.0.0.1:8080/webhook \
  -H 'Content-Type: application/json' \
  --data-binary @записанный-запрос.json
```

⚠️ Тайминг, записанный так, **не включает сеть**. Разница между локальным замером и 4,5 с — это
целиком задержка доставки.

### Логировать `request_id`

`X-Request-Id` есть только в навыках Умного дома. В обычном навыке его нет, поэтому для
связывания «жалоба пользователя ↔ запись в логе» используйте `session.session_id` и
`session.message_id` — и записывайте их **на каждом** ходе, включая отказы.

### Логировать ответ

Ответ, который не отправился, не виден нигде. Частая ошибка — логировать только вход и не логировать
результат; потом нельзя понять, был ли ответ 200.

## Что делает платформа помимо молчания

Два правила, из-за которых надёжность — не «хорошо бы», а обязательно:

> На каждые 10 обращений допускается лишь 1 ошибка сервера.

> После публикации навыка Яндекс Диалоги периодически проверяют его работу. Если навык не
> отвечает несколько часов, его отключат.

Для навыка Умного дома поры жёстче: ошибка на **1 из 5** запросов либо молчание **24 часа** — и
навык блокируют.

Практический вывод: ноутбук, который спит ночью, нарушает оба правила. Для навыка, который должен
работать постоянно, это не «неудобно», а неработающая публикация.

## Чего платформа не делает

Не полагайтесь на это при проектировании:

| Ожидание | Реальность |
|---|---|
| Повторить неудачный запрос | Не документировано, повторов нет. Обработчик **обязан** быть идемпотентным |
| Следовать редиректу | Не документировано |
| Сообщить, какое поле не так | Нет |
| Показать логи | Нет |
| Пережить превышение лимита ответа | Не документировано |

Отсюда правило: **валидируйте ответ у себя, до отправки**. Проверьте, что уложились в 5000
символов, что `end_session` и `version` на месте, что JSON собирается. Платформа это не проверит
и не объяснит.
