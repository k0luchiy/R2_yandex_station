# Навыки Умного дома

Отдельная платформа внутри Яндекс Диалогов: другой протокол, другой таймаут, другая модель
состояния. Если навык не управляет устройствами, этот файл можно не читать.

## Сначала три развеянных мифа

| Миф | Реальность |
|---|---|
| «Навыки Умного дома работают по MQTT, топики `v1.0/skills/<skill_id>/…`» | **В официальной документации нет ни одного упоминания MQTT.** Поиск `v1.0/skills` по GitHub не даёт релевантных результатов |
| «Колбэк приходит на `/v1.0/user/devices/callback`» | **Такого эндпоинта нет.** Он отдаёт 404. Колбэки только исходящие |
| «Есть Actions API v2 вместо v1» | Для навыков v1.0 — единственный протокол. Actions API существует, но для сторонних пользовательских приложений, не для навыков |

Собственная формулировка Яндекса:

> Для таких уведомлений необходим асинхронный протокол. В Яндекс Диалогах он не используется.

## Транспорт

Два варианта:

| Транспорт | Когда |
|---|---|
| REST | обычный HTTPS-эндпоинт |
| JSON-RPC 2.0 | только через Yandex Cloud Functions: `POST https://functions.yandexcloud.net/<function_id>?integration=raw` |

Методы JSON-RPC: `unlink`, `discovery`, `query`, `action`, плюс `api_version` и
`headers.{request_id, authorization}`.

## Эндпоинты

Пути **добавляются** к адресу из консоли, относительные:

| Метод | Путь | Назначение |
|---|---|---|
| `HEAD` | `/v1.0/` | проверка доступности, ожидается `200` |
| `GET` | `/v1.0/user/devices` | список устройств (discovery) |
| `POST` | `/v1.0/user/devices/query` | запрос состояния |
| `POST` | `/v1.0/user/devices/action` | изменение состояния |
| `POST` | `/v1.0/user/unlink` | пользователь отвязал аккаунт |

Заголовки каждого входящего запроса:

| Заголовок | Обязателен | Комментарий |
|---|---|---|
| `Authorization: Bearer <токен пользователя>` | да | |
| `X-Request-Id` | да | **логируйте его** — по нему поддержка ищет инцидент |
| `Content-Type: application/json` | для POST | |

## ⚠️ Главная ловушка: разная вложенность `devices`

Запрос состояния — `devices` **на верхнем уровне**:

```json
{ "devices": [ { "id": "abc-123" } ] }
```

Действие — `devices` **внутри `payload`**:

```json
{ "payload": { "devices": [ { "id": "abc-123", "capabilities": [ ] } ] } }
```

Это подтверждено и документацией, и кодом трёх независимых реализаций. Ошибка здесь не
диагностируется — просто ничего не происходит.

## Модель устройства

Ответ discovery:

```json
{
  "request_id": "<эхо X-Request-Id>",
  "payload": {
    "user_id": "ваш-идентификатор-пользователя",
    "devices": [
      {
        "id": "socket-001",
        "name": "розетка",
        "description": "умная розетка",
        "room": "спальня",
        "type": "devices.types.socket",
        "custom_data": { },
        "capabilities": [
          {
            "type": "devices.capabilities.on_off",
            "retrievable": true,
            "reportable": false,
            "parameters": { "split": false }
          }
        ],
        "properties": [
          {
            "type": "devices.properties.float",
            "retrievable": true,
            "reportable": true,
            "parameters": {
              "instance": "temperature",
              "unit": "unit.celsius",
              "range": { "min": 0, "max": 40 }
            }
          }
        ],
        "device_info": { "manufacturer": "Producer-01", "model": "xda 1" }
      }
    ]
  }
}
```

| Поле | Лимит | Комментарий |
|---|---|---|
| `user_id` | — | **выбираете вы**, Яндекс возвращает его в колбэках |
| `custom_data` | **1024 байта** | возвращается вам же в каждом query и action |
| устройств на пользователя | **301** | |
| `manufacturer`, `model` | по 256 символов | обязательны для сертифицированных |

`custom_data` — удобное место для кэша собственных идентификаторов: устройство приходит обратно
в каждом запросе, и вам не нужно заново разбирать своё состояние.

## Возможности и свойства

**Возможностей — пять** (шесть в коде), **свойств — два**.

| Возможность | Экземпляры |
|---|---|
| `devices.capabilities.on_off` | `on`; параметр `split` разделяет включение и выключение |
| `devices.capabilities.color_setting` | `hsv`, `rgb`, `temperature_k`, `scene` |
| `devices.capabilities.mode` | зависит от типа устройства |
| `devices.capabilities.range` | `brightness`, `temperature`, `volume`, `humidity`, `channel`, `open` |
| `devices.capabilities.toggle` | зависит от типа устройства |
| `devices.capabilities.video_stream` | **только в коде**, в таблице документации отсутствует |

| Свойство | Экземпляры |
|---|---|
| `devices.properties.float` | `temperature`, `humidity`, `pressure`, `illumination`, `tvoc`, `battery_level`, `water_level`, `food_level`, `amperage`, `voltage`, `power`, счётчики |
| `devices.properties.event` | `motion`, `door`, `smoke` и прочие |

⚠️ **Нет возможности `temperature` и нет «яркости света».** Яркость — это `range` с
`instance: brightness`. Температура — либо `range`/`temperature` (управляемая), либо
`properties.float`/`temperature` (только чтение). Путаница между ними — классическая ошибка.

Форма состояния: `payload.devices[].capabilities[]` = `{type, state: {instance, value}}`.
Отдельных объектов `state` или `properties_state` **нет** — `state` лежит внутри каждой
возможности.

## Колбэки

Только исходящие: вы отправляете Яндексу, Яндекс вам не звонит.

| Путь | Когда |
|---|---|
| `POST https://dialogs.yandex.net/api/v1/skills/{skill_id}/callback/state` | состояние изменилось, устройство ушло в оффлайн |
| `POST https://dialogs.yandex.net/api/v1/skills/{skill_id}/callback/discovery` | изменились параметры устройств |

| Параметр | Значение |
|---|---|
| Авторизация | `Authorization: OAuth <токен владельца навыка>` — схема **`OAuth`**, не `Bearer` |
| Токен | Yandex OAuth владельца навыка, `response_type=token` |
| Кто может | только создатель навыка |
| Доступно | только для **опубликованных** навыков |
| Успех | `202 Accepted` (не 200) |

```json
{
  "ts": 1602703322.1,
  "payload": {
    "user_id": "ваш-идентификатор",
    "devices": [
      {
        "id": "sensor-001",
        "status": "offline",
        "capabilities": [],
        "properties": [
          { "type": "devices.properties.event", "state": { "instance": "motion", "value": "detected" } }
        ]
      }
    ]
  }
}
```

`ts` — float, UNIX-секунды. `status` — `online` или `offline`. Требуется заполнить `capabilities`
**или** `properties`.

Отправка `offline` — единственный способ, которым устройство «уходит в оффлайн» на стороне
Алисы. Discovery для оффлайн-устройств не перезапускается; удалить устройство может только
пользователь.

## Лимиты

| Параметр | Значение |
|---|---|
| **Таймаут навыка** | **3 секунды** — целиком, включая сеть |
| **Длина ответа** | **5000 символов** |
| Устройств на пользователя | 301 |
| `custom_data` | 1024 байта |
| Токен / `expires_in` | 2048 символов / 1 … 4 294 967 296 |
| Лимиты запросов | **не опубликованы** |

Обратите внимание: **3 секунды, а не 4,5**. Если вы делаете один навык, который работает и как
обычный, и как Умного дом, ориентируйтесь на меньшее.

## Блокировка

Опубликованный навык блокируют, если он ошибается на **1 из 5** запросов, не отвечает **24 часа**
или получает жалобы.

Для обычных навыков порог мягче: не более **1 ошибки на 10 обращений** и отключение после
нескольких часов молчания.

## Оффлайн-устройства

**Никогда не отвечайте 5xx из-за устройства.** Правильный ответ — `200` с признаком:

В `query` — на уровне устройства:

```json
{ "id": "socket-001", "error_code": "DEVICE_UNREACHABLE" }
```

Присутствие `error_code` **игнорирует** `capabilities` и `properties` — это и есть сигнал.

В `action` — в `action_result`:

```json
{
  "id": "socket-001",
  "action_result": { "status": "ERROR", "error_code": "DEVICE_UNREACHABLE" }
}
```

Либо просто исключите устройство из `payload.devices`.

Полный список кодов с формулировками для пользователя — в документации, раздел
`concepts/response-codes`: `DOOR_OPEN`, `LID_OPEN`, `REMOTE_CONTROL_DISABLED`,
`NOT_ENOUGH_WATER`, `LOW_CHARGE_LEVEL`, `CONTAINER_FULL`, `DEVICE_STUCK`, `DEVICE_OFF`,
`FIRMWARE_OUT_OF_DATE`, `DEVICE_UNREACHABLE`, `DEVICE_BUSY`, `INTERNAL_ERROR`, `INVALID_ACTION`,
`INVALID_VALUE`, `NOT_SUPPORTED_IN_CURRENT_MODE`, `ACCOUNT_LINKING_ERROR`, `DEVICE_NOT_FOUND`.

## Про хаб

Роли хаба в протокол **нет**. «Хаб Яндекса» — это физическое устройство Zigbee, а не программная
роль.

Что достижимо на практике: один навык выступает **агрегирующим провайдером** и отдаёт устройства
из многих подсистем — Home Assistant, OpenHAB, Zigbee, ESP. Со стороны платформы это выглядит
как один навык с одним `user_id` и длинным списком устройств. Именно так работают все открытые
мосты.

## Про MQTT начистоту

Единственный MQTT, который operated Яндекс, — **Yandex IoT Core**. Это брокер для парка
устройств, а **не** транспорт навыков:

| Параметр | Значение |
|---|---|
| Адрес | `mqtt.cloud.yandex.net:8883`, TLS |
| Учётные данные | в консоли Yandex Cloud, **не** в консоли Диалогов |
| QoS | **только 0 и 1** |
| Топики | `$devices/<id>/events`, `/state`, `/commands`, `/config` |
| Судьба | сервис **прекращает работу 1 декабря 2026 года** |

Реальный паттерн, который используют мосты: навык говорит с Яндексом по HTTPS и переводит каждый
HTTP-триггер в публикацию в **свой** брокер. Топики — полностью ваша договорённость; никакого
`v1.0/skills/...` нет нигде.

## Сертификация

**Для публикации не нужна.** Нужна для официального статуса, размещения в Маркете и статуса
официального производителя.

Требования:

- устройство есть в Яндекс Маркете;
- контакты подтверждают, что вы официальный представитель производителя (это делает навык
  официальным);
- ID устройств в разделе «Устройства» консоли;
- пройдена модерация.

Сертификация покрывает **семейство устройств**, а не бренд. Обязательными становятся
`device_info.manufacturer` и `model`, а реализация сервиса уведомлений — **проверяемой
модератором**.

Отзыв сертификации происходит автоматически, если доля ошибок по сертифицированным моделям
превышает **5%** за четыре недели.

Устройства, требующие электромонтажа (настенные выключатели, реле, голые розетки), не
сертифицируются.

## Модерация навыка Умного дома

Два этапа:

| Этап | Срок |
|---|---|
| проверка настроек | не больше одного рабочего дня |
| видеопроверка устройств человеком | не больше часа |

Модератор проверяет, что связка работает, устройства выполняют команды, состояние меняется,
ошибок нет, **и что навык отвечает в пределах 3 секунд**.

Видеопроверка означает, что нужны тестовая учётная запись и физические устройства.
