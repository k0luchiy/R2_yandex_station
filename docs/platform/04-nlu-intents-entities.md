# NLU: интенты, слоты, сущности

Как навык различает запросы. Материал нужен, только если навык объявляет интенты; если он просто
читает `request.command` целиком, это можно пропустить.

## Что приходит в `request.nlu`

```json
"nlu": {
  "tokens": ["закажи", "пиццу", "на", "льва", "толстого", "16", "на", "завтра"],
  "entities": [
    { "tokens": {"start": 2, "end": 6}, "type": "YANDEX.GEO",  "value": { "street": "льва толстого", "house_number": 16 } },
    { "tokens": {"start": 3, "end": 5}, "type": "YANDEX.FIO",  "value": { "last_name": "толстой" } },
    { "tokens": {"start": 7, "end": 8}, "type": "YANDEX.DATETIME", "value": { "day_is_relative": 1 } }
  ],
  "intents": {}
}
```

| Поле | Формат |
|---|---|
| `tokens` | массив строк, **нумерация с нуля**; числительные уже превращены в цифры |
| `entities` | массив `{tokens: {start, end}, type, value}` |
| `intents` | **карта** `имя интента → {slots: {…}}` |

`end` в `entities[].tokens` — индекс **первого слова после** сущности, то есть правая граница
не включается. Сущности могут **перекрываться**: в примере выше `GEO` (2–6) содержит `FIO` (3–5).

## Четыре типа сущностей

В `entities[]` приходят **только** четыре типа. Пользовательские сущности туда **не** попадают —
они существуют только как типы слотов.

| `type` | `value` | Пример |
|---|---|---|
| `YANDEX.FIO` | объект | `{first_name, patronymic_name, last_name}` — всё в нижнем регистре |
| `YANDEX.GEO` | объект | `{country, city, street, house_number, airport}` |
| `YANDEX.DATETIME` | объект | `{year, month, day, hour, minute}` плюс флаги `year_is_relative`, `month_is_relative`, `day_is_relative`, `hour_is_relative`, `minute_is_relative` |
| `YANDEX.NUMBER` | **просто число** | `33`, `4.5` |

Три ловушки:

- **`YANDEX.DATETIME` — не ISO 8601.** Это набор полей с относительными флагами, а не строка даты.
- **`YANDEX.NUMBER` — голое число, а не объект.** Страница «Именованные сущности» перечисляет
  ключи `integer` и `float`, но примеры показывают `"value": 33` и `"value": 4.5`. Ориентируйтесь
  на примеры.
- **`house_number` — строка.** В одном примере это `"16"`, в другом — число. **Приводите к строке
  сами**, иначе получите `TypeError` на неожиданном типе.

## Интенты

### Встроенные

Документированы ровно четыре:

| Интент | Когда |
|---|---|
| `YANDEX.CONFIRM` | согласие |
| `YANDEX.REJECT` | отказ |
| `YANDEX.HELP` | просьба о помощи |
| `YANDEX.REPEAT` | повторить |

Приходят как `"YANDEX.HELP": {"slots": {}}` — с пустым объектом слотов. И **только если навык
объявил хотя бы один интент**: если грамматики нет, встроенные не приходят.

⚠️ **Пятый интент есть в коде, но не в документации.** `YANDEX.WHAT_CAN_YOU_DO` обрабатывается
в официальном шаблоне Яндекса `yandex/alice-skills` (файл `python/show-template/alisa.py`) и в
эмуляторе `vitalets/alice-tester`, где он привязан к фразе «что ты умеешь». Документация про него
молчит. **Обрабатывайте его, если хотите угадать поведение модерации** — проверить реакцию
Алисы стоит, а не полагаться на недокументированное поле.

### Слоты

```json
"intents": {
  "taxi": {
    "slots": {
      "where": { "type": "YANDEX.GEO", "tokens": {"start": 2, "end": 6}, "value": {"city": "Москва"} },
      "when":  { "type": "YANDEX.DATETIME", "value": {"hour": 14, "minute": 0} }
    }
  }
}
```

| Поле слота | Комментарий |
|---|---|
| `type` | `YANDEX.STRING` (по умолчанию, если `type:` не указан), `YANDEX.NUMBER`, `YANDEX.FIO`, `YANDEX.GEO`, `YANDEX.DATETIME` либо имя пользовательской сущности |
| `value` | строка, число или объект — в зависимости от типа |
| `tokens` | `{start, end}`; **встречается не всегда** — в строковых слотах примеров его нет |

### Что делать с чужим интентом

Встроенные интенты приходят на любое «да», «нет», «помощь», «повтори» **и тогда, когда
навык их не объявлял** — если объявил хоть один. Два варианта:

- объявить их в грамматике и обработать;
- если не объявлять, а интент пришёл — ** falling back на своё поведение, а не игнорировать.

Практика из реального навыка: пустой `intents` приравнивается к `yandex_default`-сценарию.

### Интенты необязательны

> Если реплика не относится ни к одному интенту, поле `request.nlu` будет пустым.

Точнее: пустым будет **`intents`**, а `tokens` и `entities` заполняются **всегда**, независимо от
грамматики. Это подтверждается примерами: в `ButtonPressed` приходит `"tokens": ["надпись","на","кнопке"]`
при пустом `intents`.

**Практический вывод:** сущности (`YANDEX.FIO`, `YANDEX.GEO`, `YANDEX.NUMBER`, `YANDEX.DATETIME`)
извлекаются бесплатно, даже если вы не написали ни одной грамматики. Интенты нужны только чтобы
**различать** намерения.

R2D2 этим пользуется: он вообще не объявляет интентов и читает `request.command` целиком, отдавая
разбор модели.

## Грамматика в консоли

DSL, полный синтаксис:

```yaml
root:
    [включи $What $Where (и $Where)*]

slots:
    what:
        source: $What
    where:
        source: $Where

$What:
    свет | кондиционер

$Where:
    .+
```

### Правила

| Правило | Что это значит |
|---|---|
| отступ | 4 пробела |
| порядок | **не имеет значения** — элементы можно переставлять |
| `[...]` | любое количество повторов в любом порядке |
| `\|` | альтернативы |
| `(word)?` | необязательная группа |
| `?` `*` `+` | квантификаторы |
| `$Name` | нетерминал |
| `%lemma` | сравнение без учёта формы слова |
| `%exact` | точное совпадение |
| `%negative` | выключить правила до отменяющей директивы |
| `%positive` | включить правила обратно |
| `source: $X` | источник значения слота |
| `type: …` | тип слота |
| `filler:` | стоп-слова |

### `filler`

```yaml
filler: что|по|на|какая|какое|надо|и|пожалуйста
```

Эти слова отбрасываются при разборе. За незначащие слова отвечает отдельный классификатор,
работающий с контекстом предложения.

### Слоты

В слот попадает **только первый** распознанный нетерминал, если он используется в интенте
несколько раз.

Строка без `type:` получает `YANDEX.STRING`:

```yaml
slots:
    phase:
        source: $Phase
    where:
        type: YANDEX.GEO
        source: $Where
```

### Директивы

Действие директивы распространяется на **все последующие** нетерминалы. Можно поставить её в начале
всей грамматики или непосредственно перед нетерминалом — тогда действует до конца отступа или до
отменяющей директивы.

Официальный пример с `%negative`:

```yaml
root:
    !(%negative) включи игру %lemma .*

%negative:
    выключи
```

### `.*` и `.+`

`.+` — «любая непустая строка», документированный вариант. `.*` используется в реальных навыках
для пропуска произвольного текста в середине фразы. Оба работают.

### Скрытие нетерминалов

Вложенное определение перекрывает внешнее — удобный приём для переопределения нетерминала внутри
конкретного контекста.

## Пользовательские сущности

```yaml
entity ChessPiece:
    values:
        king: %exact король
        queen: ферзь королева
```

Объявление сущности даёт **два** эффекта:

- `$ChessPiece` становится нетерминалом грамматики;
- `ChessPiece` становится **типом слота** — его можно писать в `type:`.

Значение слота при этом равно **ключу**, а не слову из фразы. Например, для сущности тикеров
ключ `BBG006L8G4H1` — и в `value` слота придёт именно он.

### Точность и полнота

Слова из запроса, не попавшие под грамматику, **исключаются**: незначительные слова отсекает
специальный классификатор на основе контекста. Благодаря этому точность и полнота срабатывания
растут. Побочный эффект: **неописанные слова не попадут в слот** — если слово не описано, его не
будет.

### Лемматизация и точность

```yaml
entity ChessPiece:
    lemma: true
    values:
        king: король
```

`lemma: true` распространяется на всю сущность и **не отменяется** директивой `%exact` — её надо
указать явно.

В реальных грамматиках встречается и `%lemma`, и `lemma: true` **внутри** блока `values:` — то
есть и слово, и его формы описываются явно:

```yaml
entity StockTicker:
    values:
        AAPL: %exact эпл
               %lemma эпл
```

### Грамматика и сущности — два разных объекта в консоли

Вкладка «Интенты» содержит и грамматики, и сущности отдельным подзаголовком. В реальных навыках
сущности выносят в файл `.vocab` и вставляют в редактор целиком.

## Порядок работы в консоли

```
Настройки → Интенты → Создать
  → Название   (человекочитаемое, в запрос не попадает)
  → ID         (то, что придёт в nlu.intents)
  → Грамматика (вставить текст)
  → Положительные тесты
  → Отрицательные тесты
  → Протестировать
  → Сохранить
  → Опубликовать или переопубликовать
```

**ID** — латинские символы и цифры. Документация требует именно этого, но её же примеры
используют точки и подчёркивания (`turn.on`, `random_number`) — **ориентируйтесь на то, что
принимает консоль**, то есть на реальные практики: `snake_case` без точек.

**Имя и ID — разные вещи.** Имя не попадает в запрос.

## Переопубликация обязательна

> Когда вы протестируете работу навыка, опубликуйте или переопубликуйте его для того, чтобы
> интенты стали доступны пользователям. При изменении настроек интентов навык также нужно будет
> опубликовать заново.

Это следует из документации. Часть разработчиков утверждает обратное — что интенты можно менять
только **после** первой публикации. Документация это не подтверждает, а консоль даёт редактирование
интентов в черновике. Ориентируйтесь на рабочий цикл: правите → сохраняете → тестируете →
**переопубликовываете**.

## Разбор логов — рабочий цикл

Вкладка «Обработка реплик» содержит инструмент сбора журналов запросов:

```
Настройки → Интенты → выбрать интент → «Собрать запросы»
```

Дальше — классификация собранных фраз:

| Инструмент | Что делает |
|---|---|
| **Грамматика** | проверяет конкретную фразу против грамматики, показывает, что и почему не сматчилось |
| **Семантический поиск** | находит близкие фразы в логах |
| **Близость** | показывает варианты, которые почти совпали |

Метрики в тестере грамматики — **«Точность»** и **«Полнота»** (названия из практических
документов; в официальной документации эти слова не встречаются).

Поля положительных и отрицательных тестов — **списки строк**. Практика: положительные — фразы,
которые обязаны сработать; отрицательные — похожие, которые **не должны**.

Ключевая мысль цикла: одно и то же намерение записывается по-разному, и грамматику нужно
дополнять **по факту собранных логов**, а не по замыслу.

## Что распознаётся без грамматики

Даже если интентов нет:

| Что | Откуда |
|---|---|
| `tokens` | всегда, при каждом `SimpleUtterance` |
| `YANDEX.FIO`, `YANDEX.GEO`, `YANDEX.NUMBER`, `YANDEX.DATETIME` | всегда, независимо от грамматики |
| `intent` (для навыков на Skillbox) | всегда |
| Тип слота в `slots[].type` | всегда |

Не выдаётся без объявления: ваши собственные сущности — они требуют сущности, объявленной в
грамматике навыка.

## `request.markup`

В **запросе** есть объект `markup`, и он содержит **ровно одно** поле:

```json
"markup": { "dangerous_context": true }
```

`dangerous_context` — признак опасного контекста: суицидальный контент, разжигание ненависти,
угрозы. Поле **может быть только `true`**; если признака нет, ключ отсутствует (в реальных
payload встречается `false` — документация с этим расходится).

**Что делать с этим навыку:** поле приходит, когда высказывание содержит опасный контекст.
Практически осмысленная реакция — не продолжать диалог в лоб, а передать пользователя к
человеческой помощи или завершить сессию с уместной фразой. Навык не обязан это делать, но
Игнорировать поле молча — плохое решение.

⚠️ Не путать с «разметкой-аннотацией» (`hide`, `hide_selective`, `inline`, `text`, `raw`).
**Такого поля в протоколе нет** — в документации и коде открытых навыков его не существует.

## Практический минимум

Если навык — голосовой шлюз перед LLM (как R2D2), интенты **не нужны**. Достаточно:

```python
command = (body.get("request") or {}).get("command") or ""
```

NLU стоит изучать, когда нужно **различать** намерения структурно — например, одно намерение
требует обязательный слот. Но даже тогда `entities[]` доступны бесплатно и покрывают даты,
числа, имена и адреса — то есть большую часть задач извлечения без единой строки грамматики.
