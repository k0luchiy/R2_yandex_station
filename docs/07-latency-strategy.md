# Стратегия скорости: укладываемся в 4,5 секунды

Алиса ждёт ответ **4,5 с суммарно** (сеть + наш сервер + LLM). Из них на нас
реально остаётся ~2,5 с. Документ описывает, как мы это обеспечиваем и как
обрабатываем долгие задачи.

> **Актуальность документа.** Таблица бюджета ниже и правило «один раунд»
> описывают **цепочку фолбэков** — запасной путь. Основной путь сегодня —
> голосовой ход в сессии opencode, у которого своя арифметика; она в разделе
> «Два пути» ниже. Числа задержек измерены, см.
> [11-opencode-contract.md](11-opencode-contract.md).

## Бюджет времени

| Этап | Типичное время | Кто контролирует |
|---|---|---|
| Распознавание речи + доставка запроса | ~1,0–1,5 с | Яндекс |
| Туннель + наш сервер (overhead) | ~0,1–0,3 с | Мы |
| Вызов LLM (1 раунд) | 0,5–1,5 с | Мы |
| Исполнение быстрого инструмента | 0,05–0,5 с | Мы |
| Доставка ответа | ~0,2–0,5 с | Яндекс |
| **Итого** | **2,0–4,0 с** | — |

Запас прочности достигается: коротким промптом, быстрой моделью, отсутствием
лишних раундов LLM.

## Два пути: голосовой и агентный

Это главное разделение в проекте, и оно выведено из измерений, а не из вкуса.

| | Голосовой путь | Агентный путь |
|---|---|---|
| Агент | `r2d2-voice` | `r2d2-agent` |
| Маршрут | `POST /session/{id}/message`, блокирующий | `POST /session/{id}/prompt_async`, 204 |
| Дедлайн | `R2D2_FAST_DEADLINE` = **3,2 с** | нет: сервер работает, R2D2 не ждёт |
| Что слышит пользователь | ответ голосом | «Проверяю, пришлю в телеграм.» |
| Куда уходит результат | в `text`/`tts` Алисы | в Telegram через задачу `opencode_reply` |
| Когда выбирается | тёплая сессия, без сентинела | холодная сессия, сентинел, или превышен дедлайн |

**Откуда взялся дедлайн 3,2 с.** Измерено 10 выборок на `space-bunny-free`:
p50 1.667 с, p95 2.247 с. Плюс запас — 3,2 с. Плановый fallback предписывал
`min(3.6, 4.5 − 1.2)` = 3,3 с, что совпадает в пределах шума.

**Что означает дедлайн.** Голосовой ход, не уложившийся в 3,2 с, **не
отменяется**: он продолжает работать на стороне opencode. Пользователь сразу
получает подтверждение, **а сам запрос уходит `r2d2-agent`**, и фоновый воркер
забирает ответ позже и отправляет в Telegram. Отменять было бы уничтожение уже
оплаченной работы; кроме того, `POST /session/{id}/abort` на этом пути не
вызывается никогда. На дедлайне нельзя знать, ответит запоздалый голосовой ход
или попросит агента, поэтому работа отдаётся тому, кто её делает: раньше эта
ветка только подтверждала и запрос просто исчезал.

**Два свипа этой ветки не стоят ничего на часах Алисы.** Один читает
транскрипт перед отправкой хода агенту — это и было ограничено половиной секунды
(`MARKER_TIMEOUT_S`), и он остался. Второй, чтение якоря, снятого с часов
Алисы целиком: если чтение не успел, якорь ищет фоновая задача уже после
подтверждения, а если и она не справилась — пользователь получает в Telegram
прямое сообщение, что ответ потерян. Тихая потеря ответа недопустима, а
ограниченная — да; `MARKER_TIMEOUT_S` на голосовом пути не изменился.
Проверено вживую на здоровом сервере: подтверждение этой ветки произнесено за
**594 мс** от бюджета 4,5 с, а якорь доехал через 0,69 с после него
(`qa/live-run-v5.md`). Свип остатка, который ход, переживший дедлайн, оставил в
сессии, тоже стоит только на долге: читает транскрипт лишь та сессия, чей
прошлый ход пересёк дедлайн, и читает один раз на такой ход — неудачное чтение
долг не снимает, потому что невычищенный маркер переживает ход, а потраченный
голосовой бюджет — нет.

**Холодная сессия — исключение из правила.** Первый ход в новой сессии стоит
15.5 с тела ответа и 18.6 с на стену (холодный кэш: `cache.write` 1914
токенов, из них ~3 с — запуск до первого токена). Это не влезает ни в какой
бюджет, поэтому ход с sessions_count = 0 **не ждётся вовсе**: он уходит
агенту, а пользователь получает подтверждение. На втором и последующих ходах
сессия тёплая, и голосовой путь работает.

### Как укладывается в 3,2 с

1. **Один раунд.** Голосовой агент отвечает текстом; цепочки «подумай ещё» нет.
2. **Сессия уже держит контекст.** На провод уходит только новая реплика
   пользователя, поэтому не надо ни собирать историю, ни передавать её.
3. **Короткий промпт агента.** Он в определении агента, то есть кэшируется
   сервером вместе с ним.
4. **Живой дедлайн вместо таймаута соединения.** `asyncio.wait_for` срабатывает
   первым, и вызывающий всегда получает типизированную ошибку дедлайна, а не
   сырое исключение сети.
5. **Проверка liveness с отдельным коротким таймаутом** (1,5 с), чтобы
   недоступный сервер не съедал голосовой бюджет.

## Правило «один раунд» (цепочка фолбэков)

Обычный вопрос: **один** вызов LLM → ответ. Никаких цепочек «подумай ещё».

### Быстрые инструменты + `spoken_reply`

Главный приём для инструментов:

1. LLM вызвал инструмент (например `open_app`).
2. В аргументах у него **уже есть** `spoken_reply` — готовая фраза для озвучки
   («Открываю браузер»).
3. Мы выполняем инструмент (быстро) и **сразу** возвращаем `spoken_reply`
   Алисе. **Без** второго вызова LLM.

Экономия: 1 раунд LLM ≈ 0,5–1,5 с, что критично.

### Когда нужен второй раунд (редко)

Если результат инструмента требует осмысления (например, статус системы) —
делаем **второй короткий вызов** LLM с результатом инструмента. Это укладывается
в бюджет только если сумма < 2,5 с. Если модель медленная — вместо второго
раунда отправляем «сырой» краткий итог из `ToolResult.summary`.

## Долгие задачи → фоновый воркер

Для задач, которые не успевают (или не должны) выполняться в 4,5 с:
arxiv-сводки, веб-исследования, тяжёлые скрипты, ответы агента.

Паттерн **ack-then-background** на обоих путях:

```
Алиса: «Р2, отправь сводку статей про LLM с arxiv»
  → путь 1 (фолбэк): LLM вызывает arxiv_search со spoken_reply → задача в воркер
  → путь 2 (opencode): [[NEEDS_AGENT]] в ответе → prompt_async → 204
  → Алиса: «Проверяю, пришлю в телеграм.»  (мгновенно, < 1 с)
  ...
  → воркер: arxiv → суммаризация → tg_send(«Сводка по LLM: …»)
     либо: collect_reply по сессии → tg_send(ответ агента)
  → Пользователь получает результат в Telegram
```

Плюсы:
- Алиса отвечает мгновенно, сессия не рвётся.
- Алиса не умеет «пушить» — Telegram решает проблему доставки результата.
- Тяжёлый LLM для сводки не влияет на задержку голосового ответа.

### Очередь

- `asyncio.Queue` внутри процесса + таблица `jobs` в SQLite (переживает рестарт).
- Каждая задача: `job_id`, тип, параметры, статус (pending/running/done/error),
  результат, время создания/завершения.
- Воркер — 1–2 корутины, поднятые на старте приложения.
- Лимиты: не более 2 задач одновременно; у задачи сбора ответа opencode есть
  собственный потолок (10 минут по умолчанию), и он применяется **в воркере**,
  а не оставляется на усмотрение сборщика: сборщик — это реализация, а потолок
  обещание перед всей очередью.

## Оптимизации

1. **Модель:** голосовой путь и фоновые сводки идут на `opencode/space-bunny-free`
   — единственную рабочую модель на этой машине. Отдельной сильной модели нет
   (см. [11-opencode-backend.md](11-opencode-backend.md), C1).
2. **Промпт:** компактный, версионируется в конфиге агента рядом с его
   разрешениями, а не собирается заново каждый запрос.
3. **max_tokens:** 300–400 на фолбэке. Модель не «растекается».
4. **История:** на фолбэке не больше ~20 сообщений; на голосовом пути история
   вообще не передаётся — её держит сессия.
5. **Сжатие сессии:** при росте сессии за `R2D2_SESSION_SOFT_LIMIT` она
   сжимается сервером, поэтому длинный разговор не деградирует в задержку.
6. **Спец-интенты** («помощь», «что ты умеешь», приветствие, выход)
   отвечаются фикс-строками вообще без LLM.
7. **Сеть:** туннель (cloudflared) имеет маленький overhead; сервер держим рядом
   с Яндексом.
8. **Кэш повторяющихся вопросов** (опционально): hash вопроса → ответ в SQLite
   на 24 часа (осторожно с изменчивыми вопросами).

## Измерение и мониторинг

Каждый ход пишет **ровно одну** строку в лог — в том числе когда он упал:

```
turn route=opencode path=voice model=opencode/space-bunny-free agent=r2d2-voice \
  llm_ms=1667 total_ms=1730 escalated=False permission_asked=False msgs=1 tools=()
```

| Поле | Что читать |
|---|---|
| `route` | `opencode` — сессия, `fallback` — цепочка бэкендов |
| `path` | `voice` — ответили здесь, `escalate` — ушло агенту, `deadline` — не уложилось, ответ заберёт воркер, `error` — сработала аварийная ветка |
| `llm_ms` | время модельного вызова |
| `total_ms` | весь ход |

Метрика «уложились в 3,2 с» — это доля `path=voice` среди ходов с
`route=opencode`. Если её падает, смотрим `path=deadline` и p95 в логах.
Ни одно поле не приходит из `${...}` из `config/backends.json`, поэтому ключ в
такую строку попасть не может.

**`path=error` на живом сервере — это теперь диагноз, а не «сервер был занят».**
Каждый ход начинается с перепроверки привязки сессии (`GET /session` — список
всех сессий сервера, самый крупный ответ на этом пути), и сразу после
перезапуска `opencode serve` она иногда не укладывалась в отведённое время, хотя
сервер был здоров: проба здоровья в том же ходе отвечала 200. Такое чтение теперь
разбирается как дедлайн, а не как обрыв, и ход продолжается на уже проверенной
сессии, а не падает в цепочку фолбэков. Если `path=error` вырос — смотрите
`llm_ms` и время до первой строки хода; `path=deadline` на месте означает, что
бюджет выросло у модели, и это другой разговор.

## Аварийный ответ

Если всё пошло не так (таймаут, ошибка), возвращаем валидный JSON, а не 500:

```json
{
  "response": {
    "text": "Что-то пошло не так. Попробуй ещё раз.",
    "end_session": false
  },
  "version": "1.0"
}
```

Это гарантирует, что сессия не закроется с «навык не отвечает» из-за нашей
ошибки (но лимит 4,5 с всё равно нельзя превышать). Отдельно: **отказ opencode
никогда не зачитывается вслух**. Ответ 200 с `info.error` внутри — это провал
хода, а не ответ, поэтому он уходит в цепочку, а пользователь этого хода
слышит либо ответ, либо подтверждение, либо аварийный текст.
