# Стратегия скорости: укладываемся в 4,5 секунды

Алиса ждёт ответ **4,5 с суммарно** (сеть + наш сервер + LLM). Из них на нас
реально остаётся ~2,5 с. Документ описывает, как мы это обеспечиваем и как
обрабатываем долгие задачи.

## Бюджет времени

| Этап | Типичное время | Кто контролирует |
|---|---|---|
| Распознавание речи + доставка запроса | ~1,0–1,5 с | Яндекс |
| Туннель + наш сервер (overhead) | ~0,1–0,3 с | Мы |
| Вызов LLM (1 раунд) | 0,5–1,5 с | Мы |
| Исполнение быстрого инструмента | 0,05–0,5 с | Мы |
| Доставка ответа | ~0,2–0,5 с | Яндекс |
| **Итого** | **2,0–4,0 с** | — |

Запас прочности достигается: коротким промптом, быстрой моделью, отсутствием
лишних раундов LLM.

## Правило «один раунд»

Обычный вопрос: **один** вызов LLM → ответ. Никаких цепочек «подумай ещё».

### Быстрые инструменты + `spoken_reply`

Главный приём для инструментов:

1. LLM вызвал инструмент (например `open_app`).
2. В аргументах у него **уже есть** `spoken_reply` — готовая фраза для озвучки
   («Открываю браузер»).
3. Мы выполняем инструмент (быстро) и **сразу** возвращаем `spoken_reply`
   Алисе. **Без** второго вызова LLM.

Экономия: 1 раунд LLM ≈ 0,5–1,5 с, что критично.

### Когда нужен второй раунд (редко)

Если результат инструмента требует осмысления (например, статус системы) —
делаем **второй короткий вызов** LLM с результатом инструмента. Это укладывается
в бюджет только если сумма < 2,5 с. Если модель медленная — вместо второго
раунда отправляем «сырой» краткий итог из `ToolResult.summary`.

## Долгие задачи → фоновый воркер

Для задач, которые не успевают (или не должны) выполняться в 4,5 с:
arxiv-сводки, веб-исследования, тяжёлые скрипты.

Паттерн **ack-then-background**:

```
Алиса: «R2, отправь сводку статей про LLM с arxiv»
  → LLM: tool_call arxiv_search(query="LLM", spoken_reply="Собираю сводку, пришлю в телеграм")
  → Сервер: ставим задачу в очередь (async_worker), возвращаем spoken_reply
  → Алиса: «Собираю сводку, пришлю в телеграм»  (мгновенно)
  ...
  → async_worker: arxiv → суммаризация → tg_send("Сводка по LLM: ...")
  → Пользователь получает сводку в Telegram
```

Плюсы:
- Алиса отвечает мгновенно, сессия не рвётся.
- Алиса не умеет «пушить» — Telegram решает проблему доставки результата.
- Тяжёлый LLM для сводки не влияет на задержку голосового ответа.

### Очередь

- `asyncio.Queue` внутри процесса + таблица `jobs` в SQLite (переживает рестарт).
- Каждая задача: `job_id`, тип, параметры, статус (pending/running/done/error),
  результат, время создания/завершения.
- Воркер — 1–2 корутины, поднятые на старте приложения.
- Лимиты: не более N задач одновременно, таймаут на задачу (например 120 с),
  повторная отправка в ТГ при ошибке (не больше 2 попыток).

## Оптимизации

1. **Модель:** для голосовых ответов — быстрая (Lite / small). Для фоновых
   сводок — сильная (Pro). Провайдеры описаны в [05-llm-provider.md](05-llm-provider.md).
2. **Промпт:** компактный, без лишних инструкций. System-промпт кэшируется в
   переменной (не собирается заново каждый запрос).
3. **max_tokens:** 300–400. Модель не «растекается».
4. **История:** не больше ~20 сообщений, реплики ужимаются до разумной длины.
5. **Таймаут LLM:** `timeout=3.0с` — если провайдер медленный, сразу ответ
   «Не успеваю, попробуй ещё раз» или запасной провайдер.
6. **Горячие ответы:** спец-интенты («помощь», «что ты умеешь», приветствие)
   отвечаются фикс-строками вообще без LLM.
7. **Сеть:** туннель (cloudflared) имеет маленький overhead; сервер держим в
   РФ/Европе рядом с Яндексом (для нас — просто локально в РФ).
8. **Кэш повторяющихся вопросов** (опционально): hash вопроса → ответ в SQLite
   на 24 часа (осторожно с изменчивыми вопросами).

## Измерение и мониторинг

- Каждый запрос логирует: `duration_ms`, количество LLM-раундов, провайдер,
  модель, результат.
- Метрика «уложились в 3 с» (наш целевой бюджет) — если часто вылезаем,
  снижаем модель или упрощаем промпт.
- Ошибки провайдера и таймауты — в лог и (опционально) в Telegram-отчёт.

## Аварийный ответ

Если всё пошло не так (таймаут, ошибка), возвращаем валидный JSON, а не 500:

```json
{
  "response": {
    "text": "Что-то пошло не так. Попробуй ещё раз.",
    "end_session": false
  },
  "version": "1.0"
}
```

Это гарантирует, что сессия не закроется с «навык не отвечает» из-за нашей
ошибки (но лимит 4,5 с всё равно нельзя превышать).
